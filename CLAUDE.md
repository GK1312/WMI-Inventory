## Project status

This is an early-stage Python scaffold (PyCharm project) for a WMI-based inventory tool. Most of it is still a stub:

- `app/main.py` is the project's single entrypoint, run with `python app/main.py` (not the `uvicorn` CLI). It sets up logging and starts the FastAPI HTTP API (backed by Postgres via psycopg 3) through `uvicorn.run(...)` (see "API and database" below). Everything the project runs should start from here. When the Celery worker exists it will need its own process, and the plan is to select it with a subcommand (`main.py worker`) rather than a second script.
- `app/celery_app.py` is an empty placeholder, as are the empty directories `app/api/v1`, `app/cache`, `app/pipeline`, `app/schemas`, `app/services`, `app/signatures`, and `app/tests` (created for planned structure; their intended contents aren't documented yet — ask before filling them).

Source files are kept comment-free (no `#` comments or docstrings; only a few section markers in `config.py`). Match that: don't add comments to code unless asked.

On this machine `python` is the Microsoft Store stub, not a real interpreter. Use the project venv (below), or the `py` launcher to create it.

There's no test suite yet (`app/tests/` is empty) and no linter config. The git repo's default branch is `production` (not `main`). Dependencies (`requirements.txt`): `python-dotenv`, `psycopg[binary,pool]`, `fastapi`, `uvicorn[standard]`, `cryptography`, `scapy` (raw SYN probes; needs Npcap + admin on Windows, otherwise `tcp_ping` falls back to a connect probe, which on Windows as admin also captures the SYN-ACK via a `SIO_RCVALL` raw socket to read the TTL, IPv4 only). The result has only `host`, `port`, `state`, `reachable`, `latency_ms`, `ttl`, `src_ip`. `.env` is gitignored (it holds `DB_PASSWORD`); `.env.example` is the tracked template — copy it to `.env` on a fresh checkout. Every value has an in-code default, so `app/config.py` (and the CLI) work with no `.env` at all, but the API won't start until `API_KEY_HASHES` and `CRED_ENCRYPTION_KEY` are set, and it won't reach Postgres without DB credentials. When adding a setting, add it to `.env.example` too.

## Environment

```sh
py -3.13 -m venv .venv                                   # one-time setup (project root); the existing venv is 3.13
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe app/main.py                     # API on API_HOST:API_PORT (default 127.0.0.1:8000; /docs in development)
.venv/Scripts/python.exe app/main.py tcp-ping HOST [PORT] [--timeout 2] [--no-fallback]   # one-off TCP probe, prints JSON; no PORT probes DEFAULT_PORTS concurrently
.venv/Scripts/python.exe app/core/security.py            # generate an API key + its hash for API_KEY_HASHES
.venv/Scripts/python.exe app/core/security.py encryption-key   # generate a Fernet key for CRED_ENCRYPTION_KEY
```

On Linux (planned deployment target, also a VM), the venv interpreter is `.venv/bin/python` instead of `.venv/Scripts/python.exe`, and `python3 -m venv .venv` replaces the `py` launcher. `tcp_ping` picks its method per platform at runtime:

| Platform / privileges | Method | TTL |
|---|---|---|
| Windows + Npcap (admin) | Scapy SYN probe | yes |
| Windows, admin, no Npcap | connect + `SIO_RCVALL` capture (IPv4, not loopback) | yes |
| Windows, not admin | plain connect | no |
| Linux as root, or with `CAP_NET_RAW` (e.g. systemd `AmbientCapabilities=CAP_NET_RAW`) | Scapy SYN probe (no libpcap/Npcap needed) | yes |
| Linux, unprivileged | plain connect | no |

Unspecified (`0.0.0.0`, `::`), multicast and `255.255.255.255` targets are rejected with a `ValidationError`; connect errors that mean "no path to the host" (unreachable, timeout, local firewall `EPERM`/`EACCES`, Windows `WSAEADDRNOTAVAIL` for a subnet broadcast) are reported as `filtered`, and any other connect error raises `ProbeError`.

The API can be exercised without a running server via `fastapi.testclient.TestClient(create_app(settings), base_url='http://localhost')` from `app/` (the base URL must be in `TRUSTED_HOSTS`).

Run scripts as `app/<file>.py` (not with `-m`), because modules import each other relative to `app/` (e.g. `from utils.iprange import ...`). There are no `__init__.py` files anywhere under `app/`; `utils` and `core` work as implicit namespace packages, importable as `utils.<module>` / `core.<module>` from anywhere as long as `app/` is on `sys.path` (true automatically when running `app/main.py` as a script).

To exercise `app/core/logging.py`'s environment branching ad hoc, override the `.env` values on the command line, e.g. from `app/`:
```sh
../.venv/Scripts/python.exe -c "from config import load_settings; from core.logging import setup_logging, get_logger; setup_logging(load_settings()); get_logger('x').info('hi')"
```
with `APP_ENV=staging`, `APP_ENV=production LOG_FILE=...`, or `LOGGING_ENABLED=false` set in the environment first, to see JSON-to-stdout, the rotating file handler, or silence respectively.

## Architecture

- **`app/celery_app.py`**: still an empty placeholder — inferred from the file layout to be a Celery app for running WMI queries against hosts as background tasks.
- **`app/config.py`**: loads `.env` (via `python-dotenv`'s `load_dotenv()`) and exposes a module-level `settings` singleton (`load_settings()` called at import time) — a frozen `Settings` dataclass with logging (`app_env`, `logging_enabled`, `log_level`, `log_file`), database (`db_*`), and API (`api_host`/`api_port`, `api_key_hashes`, `cors_origins`, `trusted_hosts`, `max_body_bytes`) fields; secrets (`db_password`, `api_key_hashes`, `cred_encryption_key`) are `repr=False`. It only parses/validates values — it must never open connections, since everything that imports settings (including the future Celery worker) would then need a database at import time. Malformed ints, sslmodes, or key hashes also raise `StrictError`. `APP_ENV` must be one of `development`/`staging`/`production` and `LOG_LEVEL` must be one of `core.logging.LEVELS`; either being invalid raises `core.errors.StrictError` (a config error, same category as the response-builder dispatch errors below) at import time — there is no fallback-to-default for a *present but invalid* value, only for a *missing* one. `LOGGING_ENABLED` accepts `1/true/yes/on` (case-insensitive) as truthy, anything else (or unset, defaulting to `True`) otherwise.
- **`app/core/`**: cross-cutting concerns — `errors.py`, `logging.py`, `db.py`, `security.py`.
- **`app/core/errors.py`**: the app's error hierarchy. `Severity` is an `IntEnum` — `MINOR=10 < WARNING=20 < VALIDATION=30 < STRICT=40` — gapped so new severities can be inserted later without renumbering. `AppError(message, *, field=None)` is the base exception (`field` is optional context: which field/input triggered it). One subclass per severity — `MinorError`, `WarningError`, `ValidationError`, `StrictError` — each just overrides the class-level `severity` attribute, so call sites can either catch a specific kind (`except ValidationError:`) or branch generically on `err.severity`. To add a new kind: add a `Severity` member (using a free value between existing gaps, or extend upward) and a one-line `AppError` subclass. `SecurityError` (defined here, subclassing `StrictError` directly) shows the other extension path: subclass an existing severity class to add a domain-specific kind that inherits that severity without repeating it. It's raised by `core.security.decrypt_secret`. There is deliberately no logging/handling behavior tying `AppError` to `core/logging.py` yet (no log-and-continue-vs-raise policy) — the two modules are independent so far.
- **`app/core/logging.py`**: global logging setup, driven entirely by an `app.config.Settings` passed into `setup_logging(settings, *, force=False)` (idempotent — a second call is a no-op unless `force=True`, so it's safe to call from more than one entrypoint). Defines a custom `DATA = 15` level (between `DEBUG`=10 and `INFO`=20, registered via `logging.addLevelName` and a `Logger.data(...)` method patched onto the stdlib `Logger` class) for verbose structured payloads — raw query results, full response dicts — that are noisier than `INFO` but not a full execution trace; `LEVELS` maps all six level names (`DEBUG`/`DATA`/`INFO`/`WARNING`/`ERROR`/`CRITICAL`) to their numeric values. Behavior branches on `settings.logging_enabled` and `settings.app_env`: disabled → a `NullHandler` and level set above `CRITICAL` (fully silent); `development` → human-readable text to **stderr**; `staging`/`production` → structured JSON (`JsonFormatter`) to **stdout**, and `production` additionally adds a `RotatingFileHandler` (10MB × 5 backups) writing JSON to `settings.log_file`. `setup_logging` is called by `main.py` before `uvicorn.run` (so uvicorn's startup lines use it) and again by `create_app` (a no-op then, but it covers `TestClient` use).

### API and database

Layering: `api/routes/*` (HTTP + pydantic shape limits) → `utils/query_responses` builders (domain validation, producing the insert dict) → `repositories/*` (SQL) → `core/db` (pool).

- **`app/core/db.py`**: a module-global psycopg 3 `ConnectionPool` (`dict_row` rows). Entrypoints own its lifecycle: `init_pool(settings)` / `close_pool()` (the API does this in its FastAPI lifespan). `init_pool` opens with `wait=False`, so the API starts even if Postgres is down; `ping()` backs `/health`. `get_connection()` is a context manager whose transaction commits on success and rolls back on exception. Production refuses `DB_SSLMODE` of `disable`/`allow`/`prefer`.
- **`app/repositories/`**: one thin module per table (`ip_ranges.py`, `credentials.py`) wrapping the generic CRUD in `common.py` (`insert_row`/`get_row`/`list_rows`/`update_row`/`delete_row`, keyed by table name and PK column). Table names come from `ResponseTable` values. Server-side values such as timestamps are passed as `server_values={'col': NOW}` (SQL `LOCALTIMESTAMP`), for tables with no trigger to set them. SQL uses `psycopg.sql.Identifier`/placeholders, never string formatting of values. `insert_*` takes the dict already produced by the matching `tb_*_response` builder. To add a table, follow the existing pattern: builder + `ResponseTable` entry, a repository module, and a routes module included in `v1`.
- **Schema**: tables are managed outside this repo, directly in Postgres. Don't add `.sql` files, DDL, or a migration tool to the codebase. The database is `samdb` (tables in schema `sam`, reached via `samuser`'s `search_path = sam, public`, so SQL uses unqualified table names) on Postgres 18 inside a VMware Ubuntu VM, reached from Windows at the VM's VMnet8 NAT address (`DB_HOST`, currently `192.168.100.141`, a DHCP lease). The VM's Postgres must list that address in `listen_addresses` and allow `192.168.100.1/32` in `pg_hba.conf`. `localhost` on Windows is an **unrelated** local Postgres 18 install (ports 5432/5433), and `172.28.0.1` is a Docker bridge inside the VM that isn't reachable from Windows. Before changing a model or builder, inspect the real table via `information_schema.columns`. Real names don't follow the placeholder convention. The code targets the **live** schema: `tbsysipranges` has `range_id integer GENERATED ALWAYS AS IDENTITY`, nullable `start_ip`/`end_ip`/`range_enabled` (no default; the API still requires start/end), `cred_id_range integer[]`, `last_updated_time` set by trigger `trg_tbsysipranges_lut`, foreign keys on `site_id`/`scan_engine_id`, and no unique or check constraints. A planned migration (not yet applied; `sam_inventory/sql/tbsysIPRanges.sql` already has it) switches `range_id` to `UUID DEFAULT gen_random_uuid()` and makes `start_ip`/`end_ip`/`range_enabled` `NOT NULL` (`range_enabled` default false). When it's applied:
  - Change `range_id: int` to `UUID` in `api/routes/ip_ranges.py` and `repositories/ip_ranges.py` (`common.py` already accepts `int | UUID`).
  - Make `IpRangeOut` start/end/`range_enabled` non-optional.
  - Declare `range_enabled: bool = Field(default=None)` in the request models, so an explicit `null` is rejected.
  - Change `tbAsset.ip_address_range_id` and `tblScanState.ip_address_range_id` to `uuid`, or `99_foreign_keys.sql` fails. Integrity rules the API depends on (e.g. `start_ip <= end_ip`, same IP version, int4 range) are therefore enforced in the response builders.
- **`app/core/security.py`**: API keys. Keys are random `secrets.token_urlsafe(32)` tokens; only their SHA-256 hex digests are stored (`API_KEY_HASHES`, comma-separated). `verify_api_key` compares against every hash with `hmac.compare_digest` without short-circuiting. Also holds reversible secret encryption for stored credentials: `encrypt_secret`/`decrypt_secret` use Fernet with `settings.cred_encryption_key`, and a bad token raises `SecurityError`.
- **Credentials (`tbsyscredmaster`, `/api/v1/credentials`)**: `cred_password` holds WMI login passwords the scanner must reuse, so it can't be hashed. The routes encrypt it (`_encrypt_password`) after the builder validates and before the repository writes; the future scanner must decrypt with the same `CRED_ENCRYPTION_KEY`. `CredentialOut` has **no password field**, so no endpoint ever returns it. Keep it that way. The table has no triggers, so `credentials.py` sets `cred_creation_date` (on insert) and `cred_update_date` (insert + update) itself. `cred_validated` is read-only via the API (set by validation, not clients). The builder requires `cred_domain` when `cred_is_domain` is true. `tblscanstate.cred_id` and `tbasset.last_scan_cred` reference it `ON DELETE SET NULL`. `tbsysipranges.cred_id_range` holds credential IDs with **no FK**, so the API enforces the mapping itself. The ip-range builder de-duplicates the list. Create/PATCH check every ID exists via `lock_existing_credential_ids` (`SELECT ... FOR SHARE`, in the same transaction as the write, so a concurrent credential delete blocks until the range is saved), and unknown IDs get a 422. Deleting a credential runs `DELETE` **then** `remove_credential_from_ranges` (`array_remove`) in one transaction; that order matters for the lock to close the race. Writes made outside the API can still leave dangling IDs.
- **`app/api/app.py`**: `create_app(settings)` factory. Fails closed (`StrictError`) if `API_KEY_HASHES` or `CRED_ENCRYPTION_KEY` is empty. `/health` is unauthenticated; everything else lives under the `/api/v1` router, which has `require_api_key` (`api/auth.py`, `Authorization: Bearer <key>`, 401 + `WWW-Authenticate: Bearer` on any failure) as a router-level dependency — add new routers to `v1`, not to `app`, so they inherit auth. Swagger docs are only exposed in `development`. Middleware: `TrustedHostMiddleware`, a body-size cap (`BodySizeLimitMiddleware`, a raw ASGI middleware that counts streamed bytes, so it also catches chunked uploads; it must stay the innermost middleware, because a `BaseHTTPMiddleware` between it and the router wraps its 413 in an `ExceptionGroup` that FastAPI reports as a 400), optional CORS (only when `CORS_ORIGINS` is set, no credentials), and `SecurityHeadersMiddleware` (nosniff, DENY framing, strict CSP except on docs paths, `no-store`, HSTS outside development). Exception handlers map `ValidationError` → 422 (with `field`), foreign-key violation → 422 (with `field` parsed from the `Key (col)=` detail), unique violation → 409, check violation → 422 (the last two are backstops for constraints the DB may define), `OperationalError`/pool timeout → 503, and everything else → a generic 500 with details only in the logs.
- **`app/api/routes/*.py`**: request models use `ConfigDict(extra='forbid', strict=True)` and carry only size/shape limits. For fields that are optional in the request but must never be `null`, the model declares a non-optional type with `Field(default=None)` (e.g. `IpRangeUpdate.start_ip: str = Field(default=None, ...)`): omitting the field is allowed (DB default / unchanged), but an explicit `null` fails strict validation with a 422. A `NotNullViolation` handler is the backstop; response models use `IPvAnyAddress` for `inet` columns (psycopg returns `ipaddress` objects). Endpoints are sync `def` (FastAPI runs them in a threadpool), matching the sync pool. Updates are `PATCH` only (no `PUT`): `model_dump(exclude_unset=True)` distinguishes "not sent" from an explicit `null` (which clears a nullable column). The row is read `FOR UPDATE`, merged with the changes, and run through the same full builder as create, so cross-field rules (e.g. `start_ip <= end_ip`) still hold. Only the sent columns are written. `last_updated_time` is set by the DB trigger `trg_tbsysipranges_lut`, not by the code. `DELETE` returns 204. `tbasset` and `tblscanstate` reference ranges `ON DELETE SET NULL`, so a delete is never blocked but unlinks those rows.
- **`app/main.py`**: argparse subcommands, each a `run_*(args) -> int` handler whose return value is the exit code: `api` (the default when no subcommand is given) and `tcp-ping` (calls `probes.tcp_ping.tcp_ping`, which is imported lazily so API startup doesn't load scapy; it exits 0 when the host is reachable, 3 when it isn't, 2 on a `ValidationError`, and 1 on any other `AppError`). New entrypoints (e.g. `worker`) go in as further subcommands. `api` runs uvicorn with `log_config=None` (uvicorn logs flow through `core.logging`), no `Server`/`Date` headers, and `X-Forwarded-*` trusted only from `127.0.0.1`. It binds to loopback by default; TLS is expected to be terminated by a reverse proxy.
- **`app/utils/iprange.py`**:
  - Not currently called anywhere (its only caller was the old test CLI in `main.py`); kept for the scan pipeline or an API endpoint.
  - `expand_ranges(start, end)` turns an inclusive IPv4 start/end pair into the smallest list of CIDR networks that covers it (`ipaddress.summarize_address_range`). A bad value raises `ValueError`; the wrong type raises `TypeError`.
  - `expand_hosts(networks)` flattens a `list[IPv4Network]` (e.g. from `expand_ranges`) back into the individual `IPv4Address`es it covers. It iterates each network directly rather than using `.hosts()`, so network/broadcast addresses are included — this is a scan range, not a subnet, so every address in the original inclusive range must round-trip.
- **`app/utils/field_validators.py`**: reusable, per-field validation helpers shared across response builders. `validate_inet` / `validate_bool` / `validate_str` / `validate_int` / `validate_int_list(value, field_name, default=OMIT, required=False)` each type-check a value (the int validators reject `bool` and enforce the Postgres `integer` range) — raising `core.errors.ValidationError` (with `.field` set to `field_name`) on the wrong type, and `validate_inet` also on a string that isn't a valid IP address (it uses `ipaddress.ip_address`, so unlike `iprange.py` it accepts IPv6 too) — and resolve missing values one of three ways depending on the arguments passed at the call site:
  - `required=True` → raise `ValidationError` if the field is missing.
  - `default=<value>` → fill in `<value>` if missing.
  - neither passed → the field resolves to the `OMIT` sentinel, meaning "drop this key from the response entirely." `drop_omitted(dict)` filters those out and is applied at the end of every response builder.
- **`app/utils/query_responses.py`**: shapes raw data into a dict ready for a specific Postgres table insert. `create_query_response(data, table: ResponseTable)` dispatches (via the `_TABLE_BUILDERS` registry) to a `tb_<table>_response(data)` builder function. Currently only `ResponseTable.TB_SYS_IP_RANGES` (value `'tbsysipranges'`, the real table name, which `repositories/ip_ranges.py` also uses as its table identifier) → `tb_sys_ip_ranges_response`. `start_ip`/`end_ip` are required by the API (though nullable in the DB) and cross-checked by `field_validators.validate_inet_range` (same IP version, start <= end). Everything else (`range_enabled`, `range_desc`, `site_id`, `cloud_id`, `scan_engine_id` as ints, `cred_id_range` as a list of ints) is optional and only appears in the output if provided. `last_scan_time` isn't API input; it's set by scanning. To add a new table, write a `tb_<name>_response(data)` builder using the `field_validators` helpers and add one entry to `_TABLE_BUILDERS`. Dispatching on an unregistered `table` raises `core.errors.StrictError` — a dispatch/config error, distinct from the per-field `ValidationError`s the builder itself raises via `field_validators`.
- **`app/utils/other_responses.py`**: mirrors `query_responses.py`'s dispatch pattern (`create_other_response(data, kind: ResponseKind)` / `_OTHER_BUILDERS`) for response shapes that aren't a direct table insert, including raising `StrictError` on an unregistered `kind`. Currently an empty scaffold — `ResponseKind` has no members yet.

The code uses built-in generic type hints such as `list[...]` and `X | Y`, so it needs Python 3.10 or newer. Modules that use non-type values in annotations (e.g. `field_validators.py`'s `OMIT | str`) need `from __future__ import annotations` to import on Python < 3.14.
